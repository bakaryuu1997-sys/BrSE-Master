### G8 — detailed security finding (verified 2026-06-11)

Facts on disk:
- `cloudflared` in `docker-compose.yml` has **no `profiles:`**, so the tunnel
  **auto-starts** with every `scripts/start-brse-stack.sh` (it is not opt-in).
- `.run/cloudflared/config.yml` exposes two surfaces: `brse.baryuu.com` /
  `master.baryuu.com` → `frontend:3000`, and `api-brse.baryuu.com` /
  `api-master.baryuu.com` → **`backend:8000` directly**.
- `BRSE_API_SECRET` is **empty** in both `.env` and `backend/.env`;
  `APP_ORIGIN=http://localhost:3010`.
- The browser frontend (`frontend/lib/*`) calls `/api` with no `X-BrSE-Token`
  header anywhere — only the Chrome Extension has token wiring.

Risk assessment:
- **Direct backend ingress** (`api-*.baryuu.com → backend:8000`): SAFE.
  Cloudflare sets `cf-connecting-ip`, so `check_api_auth` marks the request
  remote and, with no secret configured, returns **401** instead of data.
- **Frontend-proxied path** (`brse.baryuu.com/api/* → frontend:3000 →
  backend:8000` via Next rewrite): **UNVERIFIED — potential exposure.** Safety
  depends on whether Next.js forwards `cf-connecting-ip` / `x-forwarded-for` to
  the backend hop. If it does not, the backend sees the internal hop as local
  (172.x peer) and serves protected routes without a token. Must be confirmed
  with a live external request through the tunnel.
- **Cannot be fixed by only setting `BRSE_API_SECRET`:** the browser app sends
  no token, so a bare secret would 401 the local web app. Closing the gap needs
  an infra-level control or new frontend token wiring.

**Mitigation applied 2026-06-11:** `cloudflared` is now behind the `tunnel`
compose profile and no longer auto-starts; `scripts/start-brse-stack.sh` only
brings it up when `BRSE_ENABLE_TUNNEL=1`. This removes the default public
exposure. Still recommended before ever enabling the tunnel: add Cloudflare
Access and/or set `BRSE_API_SECRET` with proper client token coverage.

Recommended mitigations (pick one; nothing changed yet):
1. **Cloudflare Access (Zero Trust)** in front of all four hostnames — protects
   without touching app code and without breaking the local app. *(Recommended.)*
2. **Gate `cloudflared` behind a compose `profile`** so the tunnel is opt-in
   (`docker compose --profile tunnel up`) instead of auto-starting.
3. **Drop the direct `api-*.baryuu.com → backend:8000` ingress** and rely only
   on the frontend surface (combined with option 1).
4. Verify-only first: from an external network, expect **401** from both
   `https://api-brse.baryuu.com/api/meetings/history` and
   `https://brse.baryuu.com/api/meetings/history`. A data response from the
   second confirms the live gap.

## 4. Deep review — Meeting Note AI (2026-06-11)

Scope read: `services/meeting_processor.py`, `transcriber.py`, `summarizer.py`,
`meeting_todo_sync.py`, `meeting_job_runner.py`, `meeting_summary_pipeline.py`,

### What is genuinely strong
- **Resilience at every stage.** Whisper parallel-chunk cache resume
  (`transcriber.py:192-238`), summary map-reduce checkpoint resume
  (`summarizer.py:67-165`), startup auto-resume of interrupted jobs
  (`main.py mark_interrupted_meeting_jobs`), cooperative cancellation
  (`ensure_not_cancelled`), and **local fallbacks at every AI step** so a memo is
  always produced even when 9router fails.
- **Long-transcript handling.** Map → hierarchical reduce with parallel workers
  (`summarizer.py:258-296`).
- **Glossary both ways.** Relevant terms injected into the prompt
  (`summarizer.py:331-364`); memo glossary extracted back into canonical
  `GlossaryTerm` (`meeting_processor.py:369-385`).
- **VN/JP/EN tuning** of Whisper (initial_prompt, hotwords, VAD) and a
  memory-aware singleton model that releases on model switch (`transcriber.py:28-44`).
- **Todo drafts de-duplicated** via a deterministic fingerprint + existing-key
  set (`meeting_todo_sync.py:154-202`), feeding a review queue (good — human in
  the loop before todos are real).

### Issues & improvement proposals (prioritized)

**P0 — correctness**
- **Cloud STT segment parsing is almost certainly broken.** `transcriber.py:90-96`
  treats SDK segments as dicts (`s['start']`, `s['text']`) — the OpenAI SDK
  returns objects (`s.start`), so this raises `TypeError` whenever cloud STT
  returns segments. Also `model="whisper-1"` is hardcoded (9router may not expose
  it) and there is no 25 MB upload guard. Recommend: fix attribute access, make
  the cloud model configurable, add a size check, and add a focused test/mocked
  smoke before relying on this path.
  **Update 2026-06-11:** the cloud branch is currently **unreachable** —
  `TranscriptionService` is only ever constructed with `mode="local"`
  (`meeting_processor.py:163`, `meetings_process.py:146`), so the bug is latent
  (no live impact today) but the advertised "Cloud STT fallback" does not
  actually work. Left for a dedicated fix (a spawned task chip was raised); not
  patched here to avoid editing dead code mid-review.

**P1 — state model & data quality**
- **Job-state coordination.** *(Corrected 2026-06-12 after deeper reading —
  the earlier "unpopulated table / split-brain" claim was wrong.)* State is
  already coordinated: `update_status_meta()` writes the meta file **and** upserts
  `MeetingTaskStatusRecord`, and `serialize_meeting_record()` merges file + DB +
  `MeetingRecord` on read. The real issue was a few **divergence leaks**:
  `mark_interrupted_meeting_jobs()` wrote the file with a raw `json.dump`
  (bypassing the DB upsert), `clear_status_meta_fields()` didn't upsert, and the
  DB upsert swallowed errors silently. **Done 2026-06-12:** all status writes now
  route through `update_status_meta`, the upsert is file-first + logged, and the
  contract is documented in `DEVELOPER_GUIDE.md` (+ tests). A full collapse to a
  single physical store was intentionally **not** done (the file is the resilient
  hot-path write and recovery scans it on disk).
- **Auto-glossary extraction can pollute the shared canonical store.**
  `_extract_glossary_lines` keys off the substring "Glossary"/"用語集" anywhere in
  the memo and `_parse_glossary_line` splits on `:` / `/` heuristically
  (`meeting_processor.py:286-330`). Junk terms (e.g. `english="N/A"`) can land in
  `GlossaryTerm`, which the Chrome Extension also reads. Recommend: route
  auto-extracted terms through a review queue (like todo drafts already have) or
  tighten validation before writing canonical glossary.
- **No focused unit tests for the core heuristics.** `priority_for_action`
  (date math + phase pressure), `is_useful_action_task` (length/noise filters),
  `_parse_glossary_line`, and the summarizer chunk/reduce logic are pure and
  bug-prone but appear untested (routes are tested, this logic is not).
  **Done 2026-06-11:** added `tests/test_meeting_heuristics.py` covering
  `priority_for_action`, `is_useful_action_task`, and `_parse_glossary_line`.
  (Summarizer chunk/reduce logic still untested — follow-up.)
- **Duplicate todo-creation paths.** `create_meeting_action_drafts` (review
  queue, used by the processor) coexisted with `auto_sync_meeting_actions_to_todo`
  + `sync_recent_completed_meeting_actions_to_todo_legacy`. The `_legacy` suffix
  signalled drift. **Done 2026-06-11:** both were dead code (no caller, no test)
  and have been removed; the review-queue path is now the only one.

**P2 — performance & robustness**
- **One DB session held for the whole job.** `_process_meeting_task_locked` keeps
  a `SessionLocal` open across transcription + summarization (minutes long),
  tying up a pooled Postgres connection while only doing AI work. Prefer
  short-lived sessions around the actual writes.
- **Parallel chunks share one Whisper model instance.**
  `_transcribe_parallel_chunks` runs a `ThreadPoolExecutor` whose workers all call
  `self.model.transcribe` on the same CTranslate2 model
  (`transcriber.py:213-238`). Verify thread-safety / CPU oversubscription vs
  `cpu_threads`×`num_workers`; consider serialising model access or a small model
  pool.
- **`_get_relevant_glossary` full-scans the glossary and substring-matches in
  Python on every summarize call** (`summarizer.py:331-364`), opening its own
  session inside the AI worker. Fine for small glossaries; will degrade as terms
  grow.
- **Detected transcript language is unused for summarization** — the memo language
  is the user-selected `language`, never reconciled with Whisper's detected lang.
- **Fragile yt-dlp progress parse** (`meeting_processor.py:547-553`) and many
  hardcoded progress percentages couple the UI to exact step numbers.

## 5. STT engine roadmap (2026-06-12)

### Is FunASR "the best"? Honest take for *this* project
FunASR (Alibaba) is genuinely excellent — **Paraformer** is SOTA-fast for
Mandarin, and **SenseVoice** is strong multilingual (zh/ja/ko/en) with built-in
emotion/event tags. **But** for a BrSE cockpit that is heavily **VN/JP/EN mixed**:
- **Vietnamese support is weak/absent** in FunASR/Paraformer/SenseVoice — a hard
  blocker for making it the default. Whisper handles Vietnamese well.
- The popular comparison table benchmarks **vanilla openai-whisper**, not the
  **faster-whisper (CTranslate2 int8)** this project already runs, which is far
  faster on CPU than that table implies.
- It adds heavy deps (`torch` + `modelscope` + `funasr`, ~GB).

**Verdict:** offer FunASR/SenseVoice as an **opt-in experimental engine** for
JP/EN-heavy meetings; keep faster-whisper the default. Never auto-default it.
